# Sidera

## Start here

- `docs/references/README.md` — engineering references by topic, the authoritative description of the code as committed. Read the relevant topic before touching a subsystem.
- Before editing code in a directory, read its `README.md` and those of its parents: they capture local conventions, invariants and entry points that the code alone does not show.

## Rules

- **Keep it clear**: Write code that is easy to read, maintain, and explain. The reader did not write it: names, shape and comments alone must tell them what the code does and why, and nothing may do more or other than it appears to.
- **Fix upstream, not downstream**: A defect is fixed where it originates and a missing capability is added to the module that owns it, never downstream where the symptom shows or where the caller happens to be; a downstream change is a workaround, and a workaround is not an option even when it is smaller. Every concern has exactly one home: logic is never copied, a special case is never added at a call site, a rule is never enforced in two places. If the correct fix needs a special case, a downstream check on a value upstream should already guarantee, or the same small edit scattered across many files, the shape is wrong: reshape the code upstream.
- **Upstream changes answer to every dependent**: Code that others depend on is changed on its own terms: find every dependent first, and shape the change by the module's purpose and contract, never by the convenience of the caller that exposed the need; a change that suits one caller and burdens another is downstream logic that has leaked upstream. Such a change stays inside the current task only while it preserves the module's contract, meaning its public shape, its invariants and the behavior its other callers rely on, and every dependent is verified. When the contract must change, or the dependents cannot all be verified within the task, stop and ask whether it becomes its own task, rather than deciding alone or landing the smaller wrong fix.
- **Infrastructure changes are their own task**: Shared infrastructure is any code that exists to serve many features rather than one: process-wide facilities, cross-process or cross-service protocols and contracts, shared utilities. The test is who depends on it, not where it lives. For such code the answer is always a separate task: when feature work reveals that it needs to change, stop and raise it as a separate proposal, then land it in its own commit with its own justification; never fold it silently into the feature's diff.
- **Design infrastructure and architecture ahead of need**: Design for the needs that can be foreseen, not only for today's callers. "Nothing uses it yet" is not a reason to leave out a capability, guard or boundary: the next caller may arrive the following day, and retrofitting a boundary once callers depend on the old shape costs more than building it in. Leave something out only when its requirement is still unclear, so any shape chosen now would likely be wrong, or when it is genuinely over-designed: mechanism no plausible use needs, or complexity out of proportion to what it protects. Known future features are not built ahead of their own task, but the architecture must be able to take them without a restructure.
- **Rigor in proportion to risk**: The effort a case receives follows how likely it is in real use, what it costs when it happens and how cheaply it can be fixed later, not whether it can be imagined. Avoid excessive defensive programming. For low-risk, local, easily reversible details, choose the simplest correct approach and move on; do not repeatedly explore hypothetical edge cases or compare alternatives for marginal gains. A rare case that would fail visibly and is cheap to fix gets no dedicated handling: make it fail loudly (an assertion, a log, a clear error) and move on. Full prevention is only for what is silent or irreversible, such as losing user data or leaking a secret. This does not waive necessary boundary validation or protections for data safety and irreversible harm. When one edge case starts pulling in extra probes, special paths or dedicated tests, stop and raise it with the developer: the case, how likely it is, what happens if it occurs and what handling it would cost.
- **Prior art before own design**: Before writing custom code, check the library's current documentation for a built-in option. Before settling the shape of anything larger than a local edit, such as a mechanism, a protocol, a data structure or an integration, find out how others have solved the same problem: search current documentation rather than memory, and the web, for the standard approach, the libraries that already do it and the known pitfalls, then bring back what can be used as is, what can be adapted, and what was compared and rejected with the reason, and say so in the proposal. Starting from a blank page while a well-trodden path exists is the costliest kind of rework, because it is discovered only after the work is built.
- **A dependency has to earn its place**: Finding a library that solves the problem is not a reason to add it. A library is taken only when every one of these holds: the problem is not simple enough to solve in a few lines of our own; the library's scope, transitive dependencies included, is about the size of our problem, so a large library is never brought in for one small piece of it; its license allows bundling and redistribution under ours; and it is actively maintained and widely used, so it is less likely to break under us than our own code would be. When any of these fails, write the code and record in the proposal which test the library failed.
- Everything in the repository is English: code, comments, commit messages, docs.
- Tests follow the product. When a change makes a test awkward, rewrite the test; how easy something is to test never decides a product choice.
- Every change to a protocol, format or rule updates the matching `docs/references/<topic>/` document in the same commit; a subsystem's first code adds its topic in the commit that lands it; a change that alters a directory's entry points, invariants or local conventions updates that directory's `README.md` in the same commit.
- Every reference must resolve for a future reader. Code, comments, docs and commit messages never cite the planning documents — their location, task or finding numbers, phase names or other working labels — nor another repository; none of it is in this history. Write the reason itself: what a guard prevents and why, never which item asked for it. An issue or PR link is fine when the sentence states the decision it records.

## Git workflow

- To move or rename a tracked file, use `git mv`; never delete and recreate.
- Every change is developed by default in a git worktree on its own branch, however small. It is made directly on `main` in the main checkout only when the developer asks for that in the current conversation, and changes already made in the main checkout are committed there rather than moved to a worktree. The main checkout never creates or switches to another branch: work there stays on `main`. Work that produces no commit needs no worktree.
- Commit messages: Conventional Commits (`feat(api): …`, `fix(web): …`, `docs(references): …`).
- Commit bodies carry what the diff cannot: why a non-obvious choice was made, and what breaks if someone undoes it. Omit the body when the subject line is the whole story.
